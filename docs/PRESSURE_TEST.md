## 一、加压工具

`tools/pressure_test.py`，三种模式、参数化帧率 / 时长 / 坏帧比例 / 断线频率，可独立运行。

| 模式 | 加压对象 | 说明 |
| --- | --- | --- |
| `gui` | 界面侧全链路（缓冲 → 绘图 → 日志 → 状态栏），不走网络 | 直接调 `MainWindow._on_frame` 喂真实字节载荷；`--bad-ratio` 注入短一字节的遥测帧，`--unknown-ratio` 注入 64 种未知类型帧 |
| `tcp` | 真实链路：连 `fake_mcu` 收帧，按 `--reconnect-every` 周期断线重连 | 帧从 socket 进来，经 `CommCore` 解码后进界面；验证端到端管道 |
| `reconnect` | 连接生命周期：open/close N 次 | 本地连接 churn 桩，测线程 / 句柄 / 内存累积 |

脚本自身开销的控制（任务卡第四节要求）：

- 计时只用 `time.monotonic` / `perf_counter`，不在循环里做时间字符串格式化；
- 主循环内不做字符串拼接，进度按 `--progress-interval`（默认 10 s）整行输出；
- 采样窗口化：内存与句柄每 4000 帧采一次、渲染耗时每 2000 帧测一次；
- 帧类型注入用"有限重复序列 + 取模"，不用随机数，比例精确、结果可复现。

> 一个已写进脚本注释的坑：连接 churn 桩若把对端连接留着不关，句柄会按"每轮 +1"线性上涨——
> 那是夹具的账，不是被测代码的。首版脚本就因此虚报 100 轮 +100 句柄，换成"接受即关"桩后归零。

## 二、四组实测

### 2.1 数据管道：14.4 万帧（20 Hz × 2 h 数据量）

加速等效压测：按 20 Hz 的 `t_ms` 步进连续喂 144,000 帧，不按墙钟等 2 小时。

| 指标 | 实测 |
| --- | --- |
| 喂入帧数 / 墙钟 | 144,000 帧 / 1.00 s（约 14.5 万帧/秒） |
| 环形队列 / 模型缓冲 | 20,000 / 20,000 点（两者都精确封顶，无增长） |
| 常驻内存 | 起始 93.7 MB → 封顶时 100.7 MB → 结束 101.2 MB，**封顶后仅 +0.54 MB** |
| 单帧渲染（73 次采样） | 均价 **0.85 ms**，P50 0.81 ms，P95 1.13 ms，最大 **1.80 ms**（预算 3 ms） |
| 渲染趋势 | 前 1/3 均值 0.93 ms → 后 1/3 均值 **0.79 ms**（无爬升，末段更快） |
| 线程 / 句柄 | 36 / 286，始终不变 |

真实节拍对照（20 Hz 连跑 30 s，600 帧）：墙钟 30.00 s、实测 20.00 帧/秒（节拍无漂移），
内存 94.0 → 95.1 MB，单帧渲染 1.69–2.09 ms。

**结论**：队列封顶后内存与渲染耗时都进入平台期，没有随帧数缓慢爬升的迹象；
加速路径与真实节拍路径表现一致。

### 2.2 断线重连：100 次

| 指标 | 实测 |
| --- | --- |
| 循环次数 | 100 次（另有 10 次预热，不计入基线） |
| 总耗时 / 单次 | 3.40 s / **33.9 ms** |
| 连接失败 | 0 |
| 句柄数 | **166 → 166**（净增 0） |
| 线程数 | **6 → 6**（净增 0） |
| 常驻内存 | 26.0 → 26.7 MB |

预热的存在是刻意的：首轮会触发解释器 / socket 的一次性分配（约 +3 句柄），
不预热就会把"一次性 +3"误读成"每轮泄漏"。

**结论**：连接生命周期没有累积，线程与句柄都回到基线；真实拔插一天几十次不会把资源耗光。

### 2.3 日志边界：2 万帧混合注入

注入构成：10,000 条坏帧（遥测载荷少一字节，长度预检失败）+ 5,000 条未知类型帧（64 种轮转）
+ 5,000 条正常遥测。

| 指标 | 实测 | 说明 |
| --- | --- | --- |
| 日志总行数 | **242 行** | 上限 2000，远未触及 |
| 解析异常日志行 | **101 行** | 对 10,078 次累计异常，约 10 行/千次（卡8 限流生效） |
| 状态栏累计计数 | 10,078 | 与日志行数解耦，保留"本机发生过多少次"语义 |
| 聚合状态表 | 62 项 | 类型空间上界 256，不可能无限增长 |
| 撞上限行为 | 直接写 3,000 行 → 恰好 2000 行；最新一行保留、最旧行被淘汰 | 丢最旧而非阻塞写入 |

**结论**：长时间偶发坏帧不会把日志与聚合状态撑爆；即使持续雪崩，也会在 2000 行处封顶。

### 2.4 时间戳回绕：32 位毫秒跨 `2^32`

构造三个连续样本（回绕前一帧 `2^32-1`、回绕点 `0`、回绕后一帧）并前后各补两点，共 7 帧，
时间跨度约 0.6 s。

| 指标 | 实测 | 期望 |
| --- | --- | --- |
| 内部横轴 x | `0.0 … -4,294,966.7 s` | 单调递增、跨度约 0.6 s |
| 单调性 | **False** | True |
| 视口跨度 | **4,294,964.7 s**（约 49.7 天） | 约 0.6 s |
| 时间窗切片 | `窗口=10s/60s/全部` 三种设置结果相同 | 10 s 窗只应保留最近 10 s |

更现实的触发路径（同一会话内 MCU 复位、上位机未清空曲线就直接重连）：

| 阶段 | 视口 | 内部 x |
| --- | --- | --- |
| 复位前（10 s 窗） | `[-0.20, 10.15]`，跨度 10.35 s | 正常 |
| 复位后（同 10 s 窗） | `[-989.05, -1.00]`，跨度 **988.05 s** | 前段 0.00 s → 末段 -990.05 s，非单调，保留 400 点（10 s 窗应约 200 点） |

也就是说，**不需要连续跑 49.7 天**：拔一次线让板子复位、上位机不清曲线直接重连，
横轴立刻跳到 -990 s 附近，最近十几秒的曲线被压到视口边缘，时间窗彻底失效。

### 2.5 P-01 根因定位（供修复卡使用）

- `pc/serialpid/gui/plot_panel.py:227`
  `row = ((sample.t_ms - self._t0) / 1000.0, ...)` —— 直接用 32 位原始毫秒减首个样本的基准，
  既不做 `2^32` 模运算，也不处理"基准回退"。
- `pc/serialpid/gui/plot_panel.py:242` `clear()` 会把 `_t0` 置空，这是唯一的重置入口。
- `pc/serialpid/gui/main_window.py:167` `_on_connection()` 在连接成功后只改按钮文字，
  **不重置绘图时间基准**，所以"板子复位 → 重连 → t_ms 归零"这条路径没有任何防线。
- 下游依赖横轴单调性的地方：`plot_panel.py:416` 的窗口起点 `np.searchsorted(full[:, 0], cutoff)`、
  `plot_panel.py:355` 的抽稀桶号映射（均以"xa 单调"为前提），以及 pyqtgraph ViewBox 自动量程。
  数据非单调时这三处一起退化：切片起点落到数组首元，整段旧数据被当成"最近窗口"画出来。

### 2.6 修复复核（card11，2026-11-07 · 对应 P-01）

上文第二节的行号指修复前版本。修复落在 `pc/serialpid/gui/plot_panel.py` 与
`pc/serialpid/gui/main_window.py` 一处：

- 内部横轴由「当前原始毫秒 − 首帧毫秒」改为「原始 u32 毫秒 + 回绕补偿 − 会话零点」；
- 负跳变按幅度分流：`|Δ| ≥ 2^31` 判**回绕**（补 `2^32`，同一会话继续画），
  否则判**复位**（按新会话重开：清旧数据、零点挪到当前帧、横轴从 0 起算），
  不再"取模"式补偿——复位时取模会把负差值变成巨大正数，比原缺陷更糟；
- 时间轴重启收敛到唯一入口 `restart_timeline()`：**连接建立 / 检测到复位 / 手动清空**
  三条路径共用，`_on_connection()` 连接成功时调用它，补上"复位 → 重连"这条防线。

## 五、未覆盖与限制

- **加速等效 ≠ 真实长跑**：14.4 万帧是把 2 小时的数据量压进 1 秒，验证的是"数据量封顶后是否退化"，
  不是"真实 2 小时墙钟里定时器、GC、Qt 事件循环的长时间行为"。真实 2 小时需单独排期。
- **离屏 + 同步渲染**：`render_now()` 直接触发重画，跳过了 30 fps 定时器的排队与合并；
  真实界面的重画频率上限更低，通常更宽松。
- **并发负载**：测量时机器上有其它任务卡并行跑测试与打包，单帧耗时可能被抬高；
  本报告的时间数字应视为**上界**而非最优值。
- **真实串口拔插未验证**：无硬件，只有 TCP 路径与本地连接 churn 桩；串口读超时 / 空闲超时路径
  由既有 `test_comm_disconnect` 用例（静默对端触发超时）覆盖，但物理拔插的驱动层行为仍属硬件待验项。
- **偶发失败按实记录、未用重试掩盖**：见 P-03，已定位到测试断言时序并加固，未改动实现。
